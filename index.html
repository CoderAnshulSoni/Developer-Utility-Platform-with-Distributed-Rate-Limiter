What We Built

A complete developer productivity platform built as a real microservices system

What is this project?

A self-hosted, highly performant developer tooling platform consisting of two Spring Boot microservices working in active tandem. Designed to streamline common database engineering, REST execution, and security tasks while maintaining distributed API throttling across all clients.

⚡

Rate Limiter Service (Port 8081)

Protects all API endpoints using Token Bucket and Sliding Window algorithms. Backed by Redis for distributed state.

🛠️

Developer Toolkit Service (Port 8080)

Four modules — SQL Analyser, Endpoint Sandbox, Execution Plan Visualiser, and Audit Logger.

🔍

SQL Analyser

Detects N+1 patterns, missing indexes, full table scans. Returns severity score 0-100.

🌐

Endpoint Sandbox

Fire HTTP requests to any endpoint in real time. View status, latency, and response body.

📊

Execution Plan

Runs EXPLAIN ANALYZE on PostgreSQL queries. Highlights bottleneck nodes visually.

📋

Audit Logger

Spring AOP logs every request with correlation IDs for full distributed request tracing.

🌐 Why no AWS in this project?

This project intentionally runs fully local via Docker Compose to demonstrate deep understanding of the underlying infrastructure. AWS abstracts Redis into ElastiCache and PostgreSQL into RDS — here every layer is visible and controllable. The architecture is cloud-ready: swap Docker for ECS and localhost for managed services and it deploys to AWS in under an hour.

Interview Prep

Top Interview Questions

Questions you will be asked about this project — with strong answers

Why did you split this into two microservices instead of one monolith?
System Design ▼
The Rate Limiter needs to scale independently from the Toolkit. If SQL analysis traffic spikes, I don't want rate limiting to be affected. Also, the Rate Limiter can protect other services too — it's a reusable infrastructure component, not just a feature of the Toolkit.
How does the Dev Toolkit call the Rate Limiter?
System Design ▼
Via a synchronous REST call in the RateLimiterClient class before processing any request. The call has a hard 200ms timeout so the Rate Limiter can never slow down the Toolkit. If it times out or throws any exception, we fail open — allow the request through — and log a LIMITER_DOWN status in the audit.
What happens if Redis goes down?
System Design ▼
The Rate Limiter loses its state but because RateLimiterClient wraps every call in try-catch and fails open, the Toolkit keeps serving requests. We log LIMITER_DOWN in every audit entry so operators can see exactly when Redis was unavailable. In production you'd add Redis Sentinel or Cluster for high availability.
How would you scale this to handle 1 million requests per day?
System Design ▼
The Rate Limiter is already horizontally scalable because all state lives in Redis. You'd run multiple Rate Limiter instances behind a load balancer — they all read and write the same Redis keys so limits are consistent. For the Toolkit, the SQL Analyser is stateless so it scales horizontally too. The bottleneck would be PostgreSQL for audit logs — you'd add read replicas and archive old logs.
How does Spring AOP work in your audit logger?
Java/Spring ▼
I used @Around advice with a pointcut matching all controller methods. Before the method runs, I generate a UUID correlation ID and call the Rate Limiter. After it runs, I calculate latency and save everything to PostgreSQL. @Around is the right advice type here because I need to wrap the method — measure time before and after — which @Before or @After alone can't do.
Why did you use HandlerInterceptor in the Rate Limiter instead of a Filter?
Java/Spring ▼
HandlerInterceptor runs after Spring's DispatcherServlet resolves the handler, so I have access to the handler method metadata. A Filter runs before DispatcherServlet and knows nothing about Spring MVC. For rate limiting I needed the mapped endpoint path like /api/sql/analyse, not the raw request URI, so HandlerInterceptor was the right choice.
How is Redis used differently by Token Bucket vs Sliding Window?
Java/Spring ▼
Token Bucket uses a Redis Hash to store two fields — current token count and last refill time. Sliding Window uses a Redis ZSet (sorted set) where each member is a request timestamp and the score is the same timestamp. This lets me efficiently remove entries older than the window using removeRangeByScore and count active entries with zCard — both O(log N) operations.
When would you choose Token Bucket over Sliding Window?
Algorithms ▼
Token Bucket allows controlled bursting — a client can fire several requests quickly as long as they accumulated tokens during quiet periods. This is ideal for the SQL Analyser where a developer might run 5 queries in quick succession. Sliding Window is strict — it counts every request in the last N seconds with no burst allowance. This is better for /api/sql/explain which hits the real database and has high cost per request.
What is the N+1 query problem and how does your SQL Analyser detect it?
Algorithms ▼
N+1 happens when you fetch N parent records and then fire one query per record to get children — N+1 total queries instead of one JOIN. My analyser looks for SELECT statements nested inside loops by detecting repeated identical SELECT patterns in the SQL string. It's a static analysis approach — not perfect but catches the most common cases. The fix is to use a JOIN or a batch fetch.
What is fail-open vs fail-closed and which did you implement?
Resilience ▼
Fail-open means if the Rate Limiter is down, requests are allowed through. Fail-closed means all requests are rejected if rate limiting is unavailable. I chose fail-open because the Rate Limiter is a supporting service — its job is to protect, not to gatekeep. If it fails, the cost is that some requests get through without rate limiting. The cost of fail-closed would be complete downtime of the Toolkit whenever Redis has a hiccup — unacceptable for a developer tool.
Why PostgreSQL for the Toolkit and Redis for the Rate Limiter?
Database ▼
Audit logs and request history are relational — they need structured querying, filtering by correlation ID, and long-term storage. PostgreSQL is the right tool. Rate limit state is purely ephemeral counters and timestamps that need sub-millisecond reads and writes with automatic TTL expiry. Redis was built for exactly this — it's why every major API gateway uses it for rate limiting.
How do you test the audit logger without running a real database?
Database ▼
In tests I use H2 in-memory database with the test Spring profile. H2 is compatible with JPA and runs entirely in memory — no PostgreSQL needed. I also mock the RateLimiterClient with @MockBean so tests don't need the Rate Limiter service running. This gives me full integration test coverage of the AOP logging behavior in pure isolation.
